### 1.2 Conventions to follow

- **Response envelope** (`utils/apiResponse.js`): `{ success: true, ...data }` / `{ success: false, message, code? }`.
- **Errors** (`utils/httpErrors.js`): `sendError` / `sendInternalError`, never leak `error.message` on 5xx, request id in `X-Request-Id`.
- **Pagination**: `utils/queryLimits.boundedLimit(value, default, max)`.
- **Rate limits**: `express-rate-limit` with the Redis store from `utils/redis.getRateLimitStore(name)`.
- **Audit**: `utils/adminAudit.recordAdminAction()` writes to `AdminAudit` (365-day TTL) and to stdout.
- **Swagger** JSDoc blocks on routes (`config/swagger.js`).
- Flat `routes/<feature>.js` plus `utils/<feature>Service.js`; models in `models/`.

### 1.3 Authentication and authorisation (current state)

- Users sign in through `POST /api/auth/signin` (email/password) or Google OAuth. The JWT is `{ userId, tokenVersion }`, HS256, 24h.
- `middleware/auth.authenticateToken` verifies the JWT, then runs a **cached DB liveness check**. Banned or deleted users fail it, and a `tokenVersion` mismatch revokes the token (used by bans, password change and logout-all).
- **There is no platform-admin role on `User`.** `routes/admin.js` says so directly. The existing admin endpoints use a static `x-admin-key` (`ADMIN_API_KEY`) and fail closed:
  - `POST /api/admin/users/:id/ban`, `/unban`
  - `POST/GET /api/admin/entitlements/:userId[/enterprise]`
  - `POST /api/admin/companies/roles/backfill`
- `SupportAgent` is a **separate** identity (own model and JWT `{ agentId }`) used by `pages/support-admin.js` to work support tickets.
- Company-level roles (`owner/admin/member…`) exist in `Company` / `companyRoleService`. These are workspace roles, not platform roles.

**Consequence:** the admin panel needs a real, server-enforced platform-admin identity. The plan below adds a `platformRole` to `User`. Admins sign in with the normal auth flow, and every admin route checks the role **against the database** on each request. Role claims in the token are never trusted.

### 1.4 Domain data available today (and gaps)

| Design needs | Existing source | Gap |
|---|---|---|
| Users, counts, sign-ups | `User` (`createdAt`, `lastLogin`, `isBanned`, `isVerified`) | No activity history, only a single `lastLogin` |
| Subscribers, plan mix, MRR, status | `Subscription` (tier, status, pricing, start/end/nextBillingDate, provider) plus `Entitlement` | Covered |

## 4. Proposed architecture

### 4.1 Frontend: `/admin-panel`
- **Same stack as `buildrs-frontend`** so nothing new is introduced: Next.js 15 (pages router), React 18, Tailwind 3.4, zustand, lucide-react. Charts are **hand-built SVG components** (line, area, bar, segmented bar, heat-map) instead of adding a chart library.
- **Port** 3002. `/api/*` is rewritten to the backend (the same pattern as `buildrs-frontend/next.config.js`), so the browser only uses relative URLs.
- **Structure:**
  ```
  admin-panel/
    pages/  _app.js, login.js, index.js (overview), users/…, finance/index.js,
            finance/transactions/[id].js, billing/index.js, billing/plans.js,
            disputes.js, insights.js, notifications.js, settings/[tab].js
    components/ layout/ (AdminShell, Sidebar, TopBar), ui/ (Card, StatCard, Button,
            Toggle, Tabs, Table, Pagination, StatusPill, Modal, EmptyState, Skeleton,
            SearchInput, FilterMenu, Avatar, Toast), charts/ (LineChart, AreaChart,
            BarChart, SegmentedBar, HeatGrid), feature components per screen
    lib/ api.js (fetch wrapper, envelope, 401/403 handling), format.js (money, dates, UTC)
    store/ auth.js
    styles/ globals.css (tokens copied from design-tokens.css)
  ```
- **Responsive:** the designs are 1440px desktop only. Proposal:
  - ≥1280: as designed.
  - 1024–1279: the stat grid goes 4→2 and side panels stack.
  - <1024: the sidebar becomes an off-canvas drawer, tables scroll horizontally inside their card, modals go full-height, and the Dispute queue and case panel stack (the queue opens the case as a sheet).

### 4.2 Backend: inside the existing architecture

**Admin identity and authorisation**
- Add `User.platformRole: null | 'admin' | 'super_admin'`. The default is `null`, so existing users are unaffected.
- `middleware/platformAdmin.js`: `requirePlatformAdmin(...roles)` chains `authenticateToken`, then a fresh DB read of `platformRole` (short-TTL cache, invalidated on change). Non-admins get a 403. Destructive operations (refund, withdraw, settings, role changes) require `super_admin`.
- Bootstrap the first super admin with `scripts/grant-platform-admin.js <email>` (same style as `scripts/upgrade-tier.js`). Admins are never self-assignable over HTTP.
- `GET /api/admin/me` returns the admin identity for the shell.
- Existing `x-admin-key` routes keep working unchanged (ops automation). Optionally they also accept a super-admin JWT.
- `AdminAudit` gains `actorUserId` / `actorEmail`. Every mutating admin call is recorded.
- A dedicated admin rate limiter (separate from the 10/15-min key limiter, which is far too low for a UI).

**Routers** (flat, following `routes/*.js`, all mounted under `/api/admin`)
- `routes/admin.js`: existing endpoints plus `/me`.
- `routes/admin-overview.js`, `admin-users.js`, `admin-finance.js`, `admin-billing.js`, `admin-disputes.js`, `admin-insights.js`, `admin-settings.js`.
- Aggregation logic lives in `utils/admin/*Service.js` so it can be unit-tested without HTTP.

**New models (minimum required by the designs)**
- `Payment`, the transaction ledger. Written from the **already-verified** webhook path (`server/routes/billing.js` and `applyWebhookEvent`, plus the legacy Paystack/Flutterwave/Stripe verify handlers). Fields: human ref (`TXN-#####`), invoice number, user, subscription, provider, provider refs (unique `providerEventId` for idempotency), plan, interval, amountMinor, currency, status (pending/successful/failed/refunded/partially_refunded), timeline[], refunds[].
- `PlatformSettings`: a singleton document for general settings and security policy.
- `PlanCatalog`: per-tier display name, description, status (active/draft/archived) and pricing, if D2 says plans become editable.
- `Withdrawal`: if D3 approves payouts.
- `UserActivityDay` `{ userId, day }` with a unique index, upserted at most once per user per day. Only if D4 approves.
- `SupportTicket` additions: `disputedAmountMinor`, `paymentId`, `activity[]` (timeline), `firstReviewedAt`, and a dispute reference (`DSP-####`) shown in the UI.

### 4.3 Testing strategy
- Jest and Supertest suites for every admin router (`tests/admin-*.test.js`), covering auth (no token → 401, non-admin → 403, admin vs super_admin), validation, pagination bounds, and the envelope shape.
- Ledger idempotency tests (webhook replays create one payment).
- The existing test suite must stay green. The admin panel gets `next build` plus a lint check.
- Manual end-to-end runs against a local MongoDB with a seed script (`scripts/seed-admin-demo.js`, dev only) to verify the populated and empty states visually against each screenshot.

## 6. Decisions needed before implementation

- **D1. Admin identity.** Proposed: `User.platformRole` (`admin` / `super_admin`) and the normal sign-in. The alternative is a separate `AdminUser` model like `SupportAgent`. Recommended: `platformRole`, because it reuses auth, liveness, bans and password policy.
- **D2. Manage Plans editability.** Prices live in code (`Subscription.tierConfigs`, `buildrs-frontend/lib/plans.js`, regional pricing). Option (a): read-only catalogue with live stats, exactly as drawn. Option (b): an editable DB-backed catalogue. - **D3. - **D4. Activity tracking for MAU and retention.** Add a lightweight once-per-user-per-day upsert in the auth path (one indexed write per user per day), or approximate from `lastLogin` only (cannot produce weekly retention). Recommended: the daily upsert.
- **D5. Platform security settings scope.** Saving the toggles is easy. **Enforcing** them means changing existing flows: password rules at signup/change, a registration gate, maintenance mode middleware, and session timeout. 2FA via an Authenticator App needs a TOTP implementation, and **SMS needs an SMS provider (none configured)**. Recommended: enforce password policy, registrations, email verification, maintenance mode and session timeout now.
